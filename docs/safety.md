# 边界检查与保护功能审计

核对日期：2026-11-20。基线为 v0.3.3（`b28513a`），包含 v0.3.4 的两项跟随保护补强。依据为仓库实际代码和自动化测试；不把界面提示、合成测试或 UART 发送确认视为真实机械位置或实物安全认证。

## 结论

项目已实现输入检查、运动请求限幅、速度约束、启动条件检查、数据新鲜度检查、固件看门狗和故障后重新确认。主要不足在于缺少实际轴位、堵转/电流、机械限位与独立电源急停反馈。

因此，它目前具备多层**软件运动约束**，还不具备能保证撞击、堵转、接错供电或驱动板失控时停止动力的完整硬件保护系统。超声波与单目深度当前是空间感知和提示功能，没有接入车轮制动链路。

## 1. 舵机与运动链路

| 检查 / 保护 | 实际实现与触发行为 | 边界与局限 |
| --- | --- | --- |
| 默认不运动 | ESP32 上电进入 `DISARMED`，GPIO17/18 为输入；不自动启用 UART、回中心或扫描。桌面启动、读取状态、开启普通视觉预览均不主动使能舵机 | 外部驱动板可能保留自己的 PWM；ESP32 待机不是动力断电 |
| 工作边界 | 桌面保存实际机构的工作区，控制器把连续角度请求钳制在工作区内，Python 传输工具再次限幅；跟随启动把本轮工作区下发给固件 | 数值必须通过具体机构测量；软件不知道实际轴有没有到位 |
| 固件绝对请求范围 | 当前普通 v0.5.3 固件 S1 为 30–175°、S2 为 0–180°。范围以外的指令拒绝；最终 6 字节 UART 帧再次校验 | S2 的 0–180°是协议允许范围，不代表装机后能安全走完整范围。用户工作区应更窄，不能直接套用 |
| 非法边界 / 中心 | 检查上下限顺序、协议范围与中心是否在工作区内；缺少有效请求参考时禁止开始实物跟随 | 保存配置不等于确认机械安全。首次定位时真实轴位未知，可能直接转向首次请求 |
| 参考状态 | 每次 MCU 重启两轴请求参考变为未知。跟随需先读取有效的两轴末次请求，且参考在工作区内；进入跟随不自动初始化或回中心 | `last_requested` 是已发送请求，不是编码器读数 |
| 跟随速度 / 加速度 | 默认上限 20°/s、80°/s²；主机控制器和固件各自限制。死区进入 1°、退出 1.8°，减少小误差下反复修正 | 是请求轨迹约束，不是实测轴速。首次未知位置初始化不享有可靠的实际运动限速 |
| 回位 / 双轴轨迹 | 固件使用五次平滑插值，名义请求速度上限 30°/s；未知参考使用显式初始化流程 | 不得据此推断机械无碰撞；轨迹内部点仍依赖矩形工作区假设 |
| 手动微调 | 界面按 1°请求；已到边界时对应按钮禁用。S2 在已观察参考区外的单轴校准，固件额外限制逐度探索 | 1°请求也可能碰撞；连续旋转舵机中的“1°”不能解释为真实位置增量 |
| 条件门控 | 需要有效固件、明确供电确认、已保存工作区、相机角度模型、安装方向确认和有效参考。改变串口会清除就绪状态；改变方向会撤销方向确认 | 供电确认是人工勾选，不是电压传感器；相机视场角快速配置只建立近似模型 |
| 小范围试跟随 | 可将本轮区间限制在参考附近半范围 2–10°，只缩小、不会扩展原工作区 | 不能替代首次方向与机械余量检查 |
| 轴与型号隔离 | 专用 `pan-locked` / `motion-locked` 固件分别锁定 S1 或全部执行器，在使能前及最终帧处拒绝受禁动作；桌面持久记录锁定 | 普通固件不具备额外锁定。不能自动识别 180°定位型和 360°连续旋转型；需要核对型号 |
| 输出故障锁存 | 串口异常、超时或协议异常会暂停执行器输出，保留视觉预览并显示原因；不因画面恢复而自动重新使能 | 继续运动前需重新读取状态、复核条件；停发不代表切断电源 |

主要实现：[ServoViewModel](../src/Toboo.Desktop/ViewModels/Hardware/ServoViewModel.cs)、[FaceAimController](../src/Toboo.Core/Tracking/FaceAimController.cs)、[FaceAimSettings](../src/Toboo.Core/Tracking/FaceAimSettings.cs)、[FaceServoSession](../src/Toboo.Desktop/Services/Hardware/FaceServoSession.cs)、[FaceFollowOutputGuard](../src/Toboo.Desktop/Services/Hardware/FaceFollowOutputGuard.cs)、[固件控制器](../firmware/esp32_single_servo/SingleServoController.h)。

### 典型工作边界处理

假设某机构已测得 S2 工作区为 50–150°，算法计算出 155°：主机限幅后的请求为 150°，传输工具再次按本轮范围处理，固件跟随模式也只允许本轮范围内的请求。目标回到区间内后可继续跟随。

这能防止正常软件链路发送越过工作区的角度目标；无法检测舵盘装反、结构在 148°就碰撞、输出轴未到位或连续旋转型舵机继续转动。

## 2. 时间、串口与异常恢复

| 检查 / 保护 | 条件与处理 |
| --- | --- |
| 单调时钟 | 控制使用单调时间；拒绝时间倒退，不以系统时间校正产生的跳变积分运动 |
| 视觉帧有效性 | 拒绝重复帧号、重复采集时间、未来帧和默认超过 200ms 的画面；坐标必须有限且位于有效图像内 |
| 丢脸 / 数据中断 | 不使用旧人脸框继续追踪；缺失和过期结果保持请求、不外推。默认更新间隔超过 150ms 时重置运动状态，避免补算大步长 |
| 目标确认 | 默认连续 3 帧确认；多人场景使用空间关联，锁定目标短暂丢失时不立即跳到另一张大脸；保留窗口默认 0.4s。这不是身份识别 |
| 最新帧优先 | 图像缓冲只保留最新待处理帧并正确释放旧原生缓冲；跟随消息队列最多一个待处理消息，避免积压旧轨迹 |
| 主机跟随超时 | 排队超过 150ms 的消息先保持再退出；250ms 未收到新主机帧则退出并尝试 `DISARM`。设备复位、会话或序号不一致也终止本轮 |
| 固件视觉目标过期 | 150ms 没有新 `FOLLOW_BOTH` 目标即保持末次请求，普通心跳不会授权继续追逐旧视觉目标 |
| 固件控制超时 | 500ms 无有效控制命令转入 `TIMED_OUT` 并关闭 UART 输出。双轴/跟随调度停顿超过 100ms 时终止；单轴调度停顿则取消未完成目标，避免恢复后补赶 |
| 重放与错误格式 | 会话带启动随机标识与使能周期，`DISARM` 后旧会话失效；序号必须递增。拒绝非法轴、状态、非数字、整数溢出、越界目标、长行和不完整行；失败命令不喂看门狗 |
| 输出链路 | UART 在发送前验证帧格式和范围，写入或传输完成超时进入故障；关闭时尽量发 `DISARM`，固件超时保护独立于电脑进程 |
| 设备占用 | ESP32 USB 统一管理，舵机与采音分别路由；本机代理仅监听回环地址且需要随机令牌，回复和音频队列有容量上限；Uno 的 LCD 与测距用同一连接串行访问 |
| 相机驱动阻塞 | 捕获异常结束会话；关闭等待驱动有期限，阻塞时要求重启应用，避免重叠打开下一路相机会话 |

依据：[跟随工具](../firmware/tools/face_follow.py)、[SharedEsp32](../src/Toboo.Desktop/Services/Voice/SharedEsp32.cs)、[TrackingSession](../src/Toboo.Desktop/Services/Vision/TrackingSession.cs)、[LatestFrameBuffer](../src/Toboo.Vision/Imaging/LatestFrameBuffer.cs)。

## 3. 超声波、建图与深度预览

| 功能 | 已有检查 | 当前实际作用 |
| --- | --- | --- |
| Uno 超声波 | 距离有效范围 20–4000mm；无回波/超范围返回无效，不能把 0 当作零距离或无限畅通；测量有 25ms 回波超时，相邻触发至少间隔 65ms | 给出前方距离与近障提示 |
| 近障建议 | 空间页默认近障阈值 350mm；读数有效期 350ms。进入近障立即建议停止，退出需超过阈值 80mm 并有两次不同的有效清除读数，降低抖动 | 是“停止建议”，没有控制车轮或切断舵机电源；没有近回波不等于路径安全 |
| 位姿与距离配对 | ArUco 位姿与测距配对窗口 140ms；位姿丢失、时间不匹配、较大平移/转向时不投影；轨迹丢定位后分段，不连出虚构路径 | 只在有效定位时累积有限的二维回波地图 |
| ArUco 几何 | 固定字典 / ID 7；至少 12 个不同棋盘格画面。检查内参、尺寸、RMS≤1.2px、标记实际边长、边缘长度、重投影误差和不合理位姿 | 不满足时没有定位；相机、分辨率、标记尺寸改变后需重核标定 |
| 内存上限 | 地图轨迹最多 2500 点，命中格最多 6000；位姿和待配对距离缓存有数量上限 | 避免无限累积导致卡顿 |
| 单目深度 | 模型 SHA-256、输入/输出格式检查；独立工作线程，一帧推理和一个待处理帧；显示相对深度和相机局部点云 | 每帧相对远近不提供可靠米制距离；暖色不能直接用于固定制动距离，也不是完整双目深度或自主 SLAM |
| 旧遥测 / 融合预览 | 独立 `uno_sensors` 协议检查握手、XOR、长度、数值范围、序号、设备时钟回绕与 250ms 积压；各通道独立失效。融合演示有姿态、近物和显式恢复锁存 | 这是另一条实验预览链路，不能与当前 LCD 合并固件下的测距提示混为一谈，更没有自动接入实物制动 |

依据：[ObstacleMap](../src/Toboo.Core/Sensors/ObstacleMap.cs)、[MarkerMappingVision](../src/Toboo.Vision/Tracking/MarkerMappingVision.cs)、[LcdRange](../firmware/uno_lcd/LcdRange.h)、[遥测与融合](../src/Toboo.Core/Sensors/SensorTelemetry.cs)、[相对深度](../src/Toboo.Vision/Tracking/RelativeDepthPreview.cs)。

## 4. 表情、LCD、语音与模型接口

| 功能 | 检查 / 保护 |
| --- | --- |
| 表情图像质量 | 人脸过小、裁边、关键点无效、侧偏/遮挡、光照过暗/过亮、模糊时不强行分类；模型输出须为七类有限数值 |
| 稳定与倾向分级 | 稳定结果默认分数≥0.60、首二类差≥0.15、持续≥0.35s；倾向默认≥0.40、差≥0.08、持续≥0.80s。原始与平滑类别需一致；丢脸、换目标、重复/过期数据清除旧标签。倾向不作为稳定情绪发送到聊天或 LCD |
| LCD 协议 | 握手、固定词表、长度与寿命校验；静态表情寿命最多 500ms，角色状态最多 1500ms，超时恢复 Unknown/待机。I²C 操作设置超时。Uno 不控制舵机 |
| 语音采集 | 检查固件身份、采音会话、序号、帧长及 CRC32；坏帧、丢帧、积压、断流取消本次输入。正常录音约 30s 上限，PCM 存储和上传最多 31s；取消会停止/清理采音 |
| 语音本地命令 | 只匹配预置完整短语「打开摄像机跟随」（忽略空白/标点），仍走正常设备、供电、方向、参考等检查，不解析任意自然语言为舵机角度。误识别仍可能发生 |
| 纠错与命令隔离 | 原始转写保留；拒绝数字/正负号、否定词变化或改动过大的纠错。改写后的文字不自动触发硬件命令，默认云端核对模式暂停自动语音命令 |
| API 与凭据 | 固定 HTTPS 地址、禁止自动重定向；请求、响应大小和时长有限制，错误提示不打印服务原始敏感内容；失败不自动重发。API Key 通过当前 Windows 账户加密存储，不进入发布包；云端录音和纠错文本会交给服务处理 |
| 行为边界 | 普通聊天回复和表情分类不会自动转换成角度请求；图片、录像和合成输入禁止连接实物跟随输出；预览与执行器路径分开 |
| 模型与发布 | 固定依赖与模型哈希，发布检查排除本地课程资料、实验数据和凭据；便携包与增量包按哈希验证，启动不自动刷固件或恢复运动 |

依据：[表情](expressions.md)、[麦克风](microphone.md)、[VoiceViewModel](../src/Toboo.Desktop/ViewModels/Companion/VoiceViewModel.cs)、[DeepSeekSpeechClient](../src/Toboo.Desktop/Services/Voice/DeepSeekSpeechClient.cs)、[TranscriptCorrection](../src/Toboo.Desktop/Services/Voice/TranscriptCorrection.cs)、[LcdProtocol](../firmware/uno_lcd/LcdProtocol.h)。

## 5. v0.3.4 的保护补强

1. **端到端帧年龄**：原跟随工具分别检查主机报告的画面年龄和本进程排队年龄，可能放过“画面 120ms + 排队 100ms”这类总年龄已超过 200ms 的目标。现在使用两者之和，过期则发送保持请求；后续新鲜目标仍能正常继续。
2. **传输启动前边界检查与冻结**：在启动串口工具之前，检查 S1/S2 边界数量、范围、上下限顺序和轴选择，并复制为本轮独立快照，防止调用方在异步启动期间改写数组、扩大本轮范围。已取消的启动请求不会再启动传输进程。下游 Python 和固件校验继续保留。

上述两项补强已纳入 v0.3.4 上位机和主机工具；v0.3.3 旧附件保持不变。升级不会放宽边界、改写本机校准或修改固件常量，无需重新烧录设备。本轮验证没有发送运动指令。

## 6. 还缺哪些保障，建议的顺序

| 优先级 | 待完善项 | 原因 |
| --- | --- | --- |
| 高 | 独立电源急停、机械限位与可靠的停机链路 | 软件挂起、驱动板保持 PWM 或通信停发时，单靠当前软件无法保证动力停止；俯仰轴失去动力后还需考虑负载下落 |
| 高 | 轴位置 / 编码器反馈、堵转电流与温度监测 | 当前不能检测“已发 90°但没转到”、持续顶住或异常发热，也不能自动确定新舵机是连续旋转型 |
| 高 | 将方向和工作区绑定到具体相机 / 机构配置，提供小范围方向复核 | 当前保存方向可以与换电脑、换摄像头或重装机构后的真实方向不符；串口号和摄像头序号不是稳定的设备身份 |
| 小车开发前 | 确定轮式底盘制动链路、实际制动距离和数据失效时的停车行为 | 当前只有提示，无轮控、实际速度反馈、制动验证或多方向盲区覆盖；不能作为已完成的小车避障控制系统 |
| 后续 | 持续在 CI 运行 Python 与 C++ 安全回归 | 现有 .NET 验证和固件构建脚本各有测试，但默认 GitHub 验证主要运行 .NET / 桥接测试。本次已手动补跑两类主机测试 |
| 后续 | 真实故障注入与可靠性记录 | 需要逐项记录断 USB、停止相机、ESP32 复位、驱动供电异常等实物表现；有损坏风险的动作应先用无执行器台架验证 |
