# PC 端视觉算法方案与 EyeTracking 框架复用分析

日期：2026 年 10 月 29 日。本文基于亚博官方教程、OpenCV／FFmpeg 文档及本地 `E:\c++\uppercomputer` 的静态源码阅读；未连接新摄像头或云台，未编译、运行或测量性能。用户说明本地版本较旧，下面对代码的判断仅针对这一份版本。

## 1. 建议结论

保留现有 C#、.NET 8、OpenCvSharp 和 Avalonia 技术路线。第一版用 OpenCvSharp 的 VideoCapture 打开 USB 摄像头，检测人工标记，计算画面偏差，再发送云台指令。FFmpeg 可继续服务于文件回放；如果最新版本已经有稳定的 DirectShow 实时采集，也可以沿用，算法层不必因此改变。

主算法采用 **ArUco 标记逐帧检测 + 中心偏差 + 比例速度控制 + 死区与限速**。不要求训练模型，也不必先做光流、Kalman 预测或通用飞行器检测。大面积色块适合先验证控制链路，CamShift 可作为后续对照。

当前重点是“测量标记在画面中的位置并使它居中”。标记中心与飞行器几何中心可以不同；标记应固定在选定的跟踪点附近。

| `DoubleBuffer` | 以两帧成组交付，存在忙轮询，读取与清空 `current` 不在同一个临界区 | 新相机采用单帧处理；改为容量为 1 的最新帧交接，并明确内存所有权 |
| `VideoEncoder` | 当前文件仅含空的 Dispose 实现 | 此版本不能作为已有录像功能的依据 |

上述缓冲问题来自静态阅读，不代表已经用压力测试复现。此轮未修改原工程。

特别注意：`StartCapture()` 中检测完成后才做水平镜像。若直接把镜像预览坐标用于控制，方向容易混淆。首版建议算法与显示都不镜像；若显示需要镜像，则仅在显示副本上进行，并明确变换关系。

## 4. 采集路径怎么选择

### 首选：OpenCvSharp 直接采集

```text
USB 摄像头
  → Windows 视频采集接口（先尝试 DirectShow）
  → OpenCvSharp VideoCapture
  → 当前图像 Mat
  → 标记检测和控制
```

这条路径利用已经存在的 OpenCvSharp，新增集成环节较少。先以设备实际支持的 640×480、约 30fps 模式试运行；控制更新先设为 10–20Hz。这些是起始配置，不是已验证性能。读取返回图像尺寸和实际时间戳，不能只相信请求参数。

### 备选：现有 FFmpeg 实时采集

FFmpeg 支持 Windows DirectShow。可先枚举设备与模式，再在 Sdcb.FFmpeg 中实现对应配置。以下命令用于到货后诊断，本文未执行摄像头采集：

```powershell
ffmpeg -list_devices true -f dshow -i dummy
ffmpeg -list_options true -f dshow -i video="实际摄像头名称"
```

不预先假定设备一定输出 MJPEG 或 YUY2，也不把任意解码缓冲直接当作灰度图。需要统一为 BGR8 或 Gray8，并保留正确的 width、height、stride 与时间戳。Mat 如果引用外部内存，必须在检测结束前保持缓冲有效；跨线程交接时可先复制，正确运行后再讨论减少拷贝。

FFmpeg 本身不保证更低延迟；实际结果取决于驱动、格式、解码和队列。两条采集路径选择其中一条即可，不同时开发两套。

## 5. 每张图像具体怎么处理

### 5.1 获取新帧并统一坐标

采集线程持续取帧，为每帧附上序号和单调时钟时间。算法繁忙时覆盖尚未处理的旧帧，不无限排队。这个策略只解决应用层积压，驱动及解码器内部延迟仍需实测。

首版固定分辨率，不随意裁剪或翻转。若需要缩放、去畸变或裁剪，之后的检测坐标、参考中心和误差计算均使用同一幅处理画面。

### 5.2 检测指定 ArUco 标记

1. 打印一张固定字典、固定 ID 的标记，四周留白，贴在平整硬板上。
2. 将彩色 Mat 转为灰度；已经是 Gray8 时直接使用。
3. 调用 OpenCV 的 ArUco 检测器，取得标记 ID 及四个角点。
4. 只保留目标 ID，排除明显过小、退化或贴近边界的候选。阈值从实测图像确定，不预设通用最小像素数。
5. 用四角坐标均值作为简单的图像中心估计，输出 `valid、u、v、角点、图像序号和时间`。

四角均值足够用于初期近正面目标居中；若要获得倾斜平面上标记物理中心的投影，应在校正后的坐标中使用对角线交点或单应变换。不要把简单均值直接称为精确的三维中心。

ArUco 检测本身包含候选四边形提取与编码判断。初期不在输入上叠加大量模糊、阈值和形态学操作，避免破坏标记。OpenCvSharp 的具体 ArUco API 名称按现有 4.10 包确认后使用，不能照搬另一大版本的方法签名。

**这一步每帧重新检测即可形成跟踪。** 不必先用上一帧预测下一帧，也不必调用一个额外的通用目标跟踪器。遮挡或检测失败时输出无效状态，不用历史位置伪装当前检测成功。

### 5.3 计算中心偏差

设当前处理画面为 W×H，目标中心为 (u,v)，参考中心为 (u₀,v₀)：

```text
ex = (u - u₀) / W
ey = (v - v₀) / H
```

首版参考中心取画面几何中心。例如 640×480 画面中，目标位于 (440,200)，则水平偏差为 +120 像素、垂直偏差为 −40 像素，对应 ex=0.1875、ey≈−0.0833。先验证云台朝向能让两个偏差减小，再进入连续闭环。

### 5.4 将偏差转为云台指令

用比例项生成转动速度，再积分为位置指令：

```text
vx = clamp(sx × Kx × deadzone(ex), -vx_max, vx_max)
vy = clamp(sy × Ky × deadzone(ey), -vy_max, vy_max)

pan_cmd  = clamp(pan_cmd  + vx × dt, pan_min,  pan_max)
tilt_cmd = clamp(tilt_cmd + vy × dt, tilt_min, tilt_max)
```

其中 sx、sy 为安装方向决定的正负号，K 的单位为“度/秒/归一化偏差”，dt 使用实际更新时间。死区内输出零速度，避免目标已居中时反复调整。程序恢复或暂停后重置计时，避免将长时间间隔直接积分为大角度动作。

先只启用水平轴，以低增益、小范围运动调试，再加入俯仰轴。角度指令不是实测轴角，因此不能用它单独证明机械角度精度。

目标丢失时停止继续沿旧误差转动，保持位置；重新检测后用限速恢复。主机停止发命令时，STM32 的独立通信超时保护也应生效。保留 STM32 适合当前硬件学习目标；直接 UART 控制驱动板可作为简化备选。

### 5.5 显示与记录

显示目标框、画面中心、偏差、检测状态和命令角度。CSV 记录时间、帧序号、检测是否有效、中心位置、偏差、命令及算法耗时。

预览和写盘不应阻塞控制。尤其不要沿用“每帧同步保存 PNG 后再检测”的配置做实时性能测试。处理 FPS、相机 FPS、应用层帧龄和实际端到端响应是不同指标，分别报告。

## 6. 其他算法是否更合适

| 方法 | 本项目中的作用 | 主要代价或局限 |
|---|---|---|
| ArUco 逐帧检测 | 正式基础方案，带 ID、便于确认目标及重复实验 | 需贴标记；过小、遮挡、倾斜和模糊会失效 |
| HSV 色块 + 形态学 + 轮廓矩 | 首次联调或低难度备选 | 相似背景颜色、光照和白平衡会影响结果 |
| CamShift | 对照实验或后续扩展 | 需要初始化外观，可能漂到背景，丢失后仍需重新检测 |
| 光流／CSRT | 更复杂的外观跟踪扩展 | 增加状态、漂移判断和重新捕获逻辑 |
| 通用检测神经网络 | 后续无标记真机扩展 | 模型、数据和目标成像大小要求会显著增加工作量 |

不建议用简单帧差／背景减除作为主方案：相机随云台转动时，背景也在移动。眼动项目中的屏幕映射与为眼部图像调节的滤波参数也不直接迁移；先完成无滤波基线，只有测得抖动确实影响控制时再加入轻量平滑，并比较新增延迟。

## 7. 标定如何加入

先在中央视野完成未校正图像上的基础跟踪，再采集棋盘格图像，估计内参与畸变参数。相机内参标定和眼动屏幕映射解决的是不同问题。

对于这款广角摄像头，应以独立验证图像上的残差和边缘效果决定畸变模型。实时阶段可预计算映射后使用 Remap，保持分辨率、镜头设置和坐标约定一致。不要每帧重新估计内参，也不按宣传的对角视场线性换算精确角度。

仅让目标在画面居中并不要求 SolvePnP 或三维姿态估计；这些可在基础实验完成后增加。

## 8. 最小实施顺序与验证

1. **固定相机检测：** 打开摄像头，识别指定 ID，保存少量原始图像和有效／无效日志；暂不连接运动控制。
2. **手动运动：** 发送有限幅度的命令，核实两轴方向、机械范围与超时行为。
3. **水平闭环：** 人工缓慢移动标记，记录偏差是否收敛以及是否振荡。
4. **双轴闭环：** 加入俯仰，调整死区和限速，统计丢失与居中比例。
5. **标定与对照：** 在明确照明、距离、标记尺寸的条件下比较校正效果及有无死区的结果。

当前无需重写完整上位机，也无需更换编程语言。下一步真正需要验证的是新相机的采集格式、图像延迟以及旧界面处理链路对闭环的影响。
